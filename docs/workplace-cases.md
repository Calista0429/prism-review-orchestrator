## 工作案例：模拟团队如何使用 PRISM

以下是基于现有功能的**虚构工作场景与可复现操作脚本**。角色对话用于解释使用方式，不代表真实用户研究；效率收益是待验证的假设，不是已经测得的工时节省。此次演练通过隔离的内存数据库和 API 验证了五个 PR 的分流、策略模拟、人工改道、审计记录和策略发布；未执行 GitHub 审批、分配审查人或合并操作。

### 演练准备与结果基线

为得到与下表一致的结果，先停止已有开发服务，再使用固定评分和临时数据库启动：

```sh
AI_PROVIDER=demo DATABASE_URL=pglite:memory pnpm dev
```

这个命令不修改 `.env`，也不覆盖 `.data/prism` 中的历史。结束演练后停止服务，再运行普通 `pnpm dev`，即可恢复 `.env` 配置的模式和数据库。使用真实 Jev 模式也能体验同样流程，但评分和分流可能不同，不应把固定案例数值当作模型承诺。

打开 Board，依次对五张卡片点击 **Run triage**，再打开详情查看 **Decision trace** 和 **Review requirements**。在默认策略 v1 下，隔离演练得到：

| PR                         | 工作内容           | 风险 / 10 | 最低维度置信度 | 分流         | 每个 PR 所需审查席位 |
| -------------------------- | ------------------ | --------- | -------------- | ------------ | -------------------- |
| `dealer-portal #142`       | 页面卡片间距调整   | 0.50      | 97%            | Fast lane    | 0                    |
| `diagnostic-gateway #87`   | 诊断状态机变更     | 7.13      | 94%            | Critical     | 2，领域审查          |
| `plant-telemetry #231`     | 生产数据库分区迁移 | 6.88      | 92%            | Critical     | 2，领域与数据库技能  |
| `vehicle-configurator #56` | 影响不明的依赖升级 | 5.63      | 43%            | Needs triage | 1，人工分诊          |
| `service-booking #109`     | 预约表单校验       | 4.13      | 91%            | Standard     | 1，常规审查          |

这里的席位是各 PR 审查要求的数量，同一个人可能被多个 PR 推荐，因此不能理解为需要六位不同的员工。Fast lane 的 0 表示 PRISM 策略不额外要求人工审查；仓库原有分支保护要求仍需满足。

### Case 1：小改动也排长队，开发者反复催审

**工作问题。** Maya 只调整了搜索结果卡片的间距，却要和生产数据库迁移一起等待负责人逐个判断。负责人需要重复阅读描述、确认测试，再告诉她下一步。

**角色演练。** Maya：“这次只改了样式，能走快速流程吗？”技术负责人对尚未评估的 `dealer-portal #142` 点击 **Run triage**；若已完成准备步骤，则直接打开详情。负责人查看变更证据：两个文件、CI 通过、无迁移、无敏感路径、负责人覆盖完整，可以通过回退提交恢复。

**系统反馈。** 固定案例风险为 0.50，低于 Fast lane 阈值 3，最低置信度 97% 高于 75%，也没有触发禁止快速通道的条件。卡片进入 **Fast lane**，详情解释原因，并提示继续检查 CI 和分支保护。

**工作方式的变化。** Maya 可以自行查看审查要求，负责人减少重复解释简单变更的流程。PRISM 不会替她批准或合并代码；如果 CI 未通过，同样的低风险评分也不能进入快速通道。

**演练完成标志。** 能从 Decision trace 说明“为什么是 Fast lane”，而不只是看到一个绿色标签。

### Case 2：负责人到处问“谁能审”，关键人员反复被打断

**工作问题。** Lena 提交生产事件表分区迁移。负责人需要找既了解业务又懂数据库的人，逐个询问技能、可用性和手头任务，很容易只找最熟悉的同事。

**角色演练。** Lena：“这次回滚需要恢复快照、重放事件，应该请谁参与？”负责人打开 `plant-telemetry #231`，查看回滚计划、迁移标记，再看 **Review requirements → Suggested reviewers**。

**系统反馈。** 该案例进入 **Critical**，需要两个审查席位，并要求 `domain` 和 `database` 技能。在初始示例人员数据下，推荐 **Aya Tanaka** 和 **Daniel Fischer**。推荐逻辑排除作者、不可用人员和达到容量上限的人员，再按现有负载比例排序。

**工作方式的变化。** 负责人先获得有依据的候选名单，再到团队实际使用的 GitHub 或沟通工具中确认和分配任务，减少无目的地找人。

**演练完成标志。** 能说明候选人为什么匹配迁移任务。推荐不会自动创建任务或发送消息，也不会预占容量；本轮五个 PR 可能重复推荐同一个人，负责人仍需协调实际排期。

### Case 3：不同负责人审查标准不一致

**工作问题。** 有人认为“测试绿了就可以”，有人认为“涉及核心业务必须双人审查”。开发者无法预判要求，交接班时还会重复争论。

**角色演练。** Kenji：“诊断状态机的测试已经通过，可以按普通改动处理吗？”值班负责人打开 `diagnostic-gateway #87`，检查 **Decision trace** 中的安全关键仓库和敏感路径证据，再对比 `service-booking #109` 的普通表单校验。

**系统反馈。** 诊断变更进入 **Critical**，需要两个领域审查席位。敏感路径或安全关键仓库会强制提高审查等级，不能仅凭 CI 通过放入 Fast lane。预约表单校验在默认策略下进入 **Standard**，需要一个常规审查席位。低置信度等条件仍可能把高风险变更转入人工分诊，同时保留双人要求。

**工作方式的变化。** 负责人围绕同一版本的策略和证据讨论例外，开发者也能在详情中看到具体要求，减少口头标准反复变化造成的返工。

**演练完成标志。** 能指出两条 PR 采用的策略版本、不同审查要求及其原因。统一执行规则不等于规则已经适合所有团队；正式使用前仍需校准阈值和路径规则。

### Case 4：信息不完整时凭经验放行，或把整个队列拖住

**工作问题。** Alex 升级了配置解析依赖，但发布说明没有解释解析优先级的变化。负责人既不想草率放行，也不希望让所有低风险变更陪着等待。

**角色演练。** Alex：“看起来只是依赖升级，为什么还不能走普通流程？”负责人打开 `vehicle-configurator #56`，查看五维评分和置信度，再检查 CI 状态与描述中的兼容性疑点。

**系统反馈。** 固定案例风险为 5.63，但最低维度置信度只有 **43%**，低于默认 75%，因此进入 **Needs triage**；CI 仍为 pending 也是不能进入快速通道的证据。模型请求失败时也会进入人工分诊，不会偷偷使用固定评分冒充真实结果。

**工作方式的变化。** 负责人把跟进聚焦为“补充优先级兼容测试、确认依赖影响、等 CI 结果”，其他 PR 可以继续各自的流程。模型不确定性成为显式待办，而不是被一个风险总分掩盖。

**演练完成标志。** 能区分“风险高”和“证据不足”。当前 Demo 尚不能在页面编辑 PR 证据或接收新 revision 的 webhook；补证工作在项目外完成，本例演练到识别问题和明确下一步，不假装已经自动闭环。

### Case 5：事后追问“为什么改道”，聊天记录难以还原

**工作问题。** 预约表单校验原本走 Standard，但发布负责人认为旺季上线前应增加领域审查。几天后团队要复盘这个决定，口头说明很容易丢失。

**角色演练。** 为保留 Case 6 的比较基线，先完成 Case 6 的模拟，再进行以下人工改道：

1. 打开 `service-booking #109` 的 **Manual override**。
2. 将 **Override route** 设为 **Critical**。
3. 在 **Override reason** 填写：`Workshop scenario: release owner requests domain review of appointment validation before the seasonal launch.`
4. 点击 **Apply override**，查看详情的 **Audit history**。
5. 打开 **Audit trail**，按 **PR ID** = `pr-booking` 筛选；也可用 **Event type** = `override` 定位这次人工决定。

**系统反馈。** PR 进入 Critical，审查人数要求升至两个，保留原有 `general` 并增加 `domain` 技能要求，自动合并资格关闭。原始评估与 Standard 分流记录仍然存在，新记录包含前后通道、原因以及关联的决策 ID。

**工作方式的变化。** 复盘时直接查看决策链，减少翻聊天记录和反复询问当事人的工作。

**演练完成标志。** 同时找到原始分流和人工改道记录。当前界面将操作人记为 `demo-operator`，没有登录认证；这个值用于演示审计结构，不能作为真实员工身份认证证据。

### Case 6：想收紧审查，却不知道会增加多少工作

**工作问题。** 流程负责人准备在发布季将更多变更送入严格审查，但不知道现有团队是否能承受新增工作。

**角色演练。** 在五个 PR 已按 v1 完成评估、尚未人工改道或发布新策略的状态下，打开 **Policy simulator**，保持 Fast lane threshold = 3、Minimum confidence = 0.75，将 **Critical threshold** 从 **6 改为 4**，点击 **Simulate draft**。

**系统反馈。** 演练验证了以下结果：

| 观察项                                    | 默认策略      | 草稿策略                               |
| ----------------------------------------- | ------------- | -------------------------------------- |
| 参与模拟的 PR                             | 5             | 5                                      |
| Fast / Standard / Critical / Needs triage | 1 / 1 / 2 / 1 | 1 / 0 / 3 / 1                          |
| 通道变化                                  | —             | `service-booking`：Standard → Critical |
| 审查席位合计                              | 6             | 8                                      |

**为什么只改一个通道，却多了两个席位？** `service-booking` 增加一个；`vehicle-configurator` 的风险也超过新 Critical 阈值，虽然因低置信度仍留在 Needs triage，却保留了更严格的双人要求，再增加一个。页面的通道变化列表只显示前者，因此还要一起看 **required reviewers** 总数。

**工作方式的变化。** 流程负责人在生效前就能看到额外审查负担，和团队讨论是否有必要、如何安排，减少策略上线后再紧急调整的反复。模拟复用已存评分，不额外调用模型，也不改变看板上的现有决定。

**演练完成标志。** 确认预览显示 **1 lane change**、**6 → 8 required reviewers**。这表示席位总需求，不是八位不同的人，也不是排期预测。若继续点击 **Publish policy**，将生成 v2，旧决定仍关联 v1，不会批量重评已有 PR；此发布行为也已在隔离 API 演练中验证。为了继续 Case 5 的原始基线，可只模拟而不发布。

### 串成一个工作日：负责人把精力用在哪里

下表是角色扮演顺序，阶段不代表实测操作时长：

| 阶段与角色            | 模拟操作                             | 留下的工作产物                                 | 可能减少的工作               |
| --------------------- | ------------------------------------ | ---------------------------------------------- | ---------------------------- |
| 晨间分诊：技术负责人  | 对五张卡片 Run triage，查看例外原因  | 1 Fast、1 Standard、2 Critical、1 Needs triage | 逐条手工分类和重复解释流程   |
| 开发跟进：Maya / Alex | 分别查看快速通道要求和不确定性原因   | 一份放行前检查清单、一份补证待办               | 催审、问状态和无目标地补材料 |
| 安排审查：技术负责人  | 查看迁移与诊断变更的技能要求、候选人 | 到实际协作工具中确认的审查安排                 | 到处询问谁能审，以及错误转交 |
| 发布准备：流程负责人  | 先执行 Case 6，比较新旧策略负担      | 一份策略预览及是否采纳的判断                   | 直接改规则后再返工           |
| 例外处理：发布负责人  | 再执行 Case 5，记录升级审查的理由    | 可检索的人工决定和历史关联                     | 靠聊天记录交接与回忆原因     |

这些案例展示的是**减少分诊、协调、解释和追溯成本的机制**。PRISM 不替代实际代码审查、测试或专业判断；现阶段也没有自动同步 GitHub、通知、任务分配或合并功能。

### 如何验证效率收益，而不是只看演示效果

正式接入工作流后，可在相似风险、规模和人员配置的 PR 上比较以下指标。当前 Demo 不自动采集全部指标，需要真实平台事件或人工计时：

| 待验证的指标         | 记录方法                                                   | 判断时需要同时关注                 |
| -------------------- | ---------------------------------------------------------- | ---------------------------------- |
| 负责人分诊耗时       | 记录每条 PR 判断通道与审查要求的人工投入分钟数             | 节省是否被后续纠错抵消             |
| 首次人工审查等待时间 | 从可审查状态到首次实质性人工审查的时间；Fast lane 单独统计 | 风险等级、工作时段与团队负载       |
| 分流纠正比例         | 记录人工纠正的数量、占比和原因，区分误判与业务例外         | 不能仅凭 override 次数认定模型错误 |
| 决策追溯耗时         | 给定一条历史 PR，计时找到当时策略、证据与调整理由          | 是否能完整解释，而不只是找到事件   |

如果分诊和等待时间下降，同时误分流、漏审与后续缺陷没有增加，才有证据说明工作效率得到改善。本文没有宣称已实现任何百分比的提升。
